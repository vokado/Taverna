## Единое техническое задание

**Статус:** проектное ТЗ, версия 1.0 (редакция 1)  
**Дата:** 14 ноября 2026 года  
**Основание:** утверждённые решения восьми этапов концептуального проектирования  
**Тип проекта:** локальное однопользовательское веб-приложение для Windows

Конкретные библиотеки, схемы и численные значения, не согласованные отдельно, считаются проектными предложениями и уточняются при техническом проектировании без изменения функционального объёма.

# 1. Назначение и границы проекта

## 1.1. Цель

Создать самостоятельный русскоязычный аналог SillyTavern под названием «Таверна» для длительного общения с локальными ИИ-персонажами, интерактивных историй и сюжетных ролевых игр. Основным текстовым движком служит LM Studio, запущенный на том же компьютере. Продукт ориентирован на одного пользователя; облачный аккаунт, подписка, интернет-сервис и постоянное сетевое соединение не требуются.

## 1.2. Требования верхнего уровня

- **GEN-001.** Поддерживаемая целевая ОС — Windows; интерфейс работает в локальном браузере.
- **GEN-002.** Единственный пользователь, без обязательной регистрации и многопользовательской сетевой инфраструктуры.
- **GEN-003.** Интерфейс, сообщения об ошибках, встроенная справка и документация — на русском языке; содержимое пользовательских карточек и историй может быть на любом языке.
- **GEN-004.** Основной внешний текстовый движок — установленный отдельно LM Studio. «Таверна» не загружает, не выгружает и не скачивает модели LM Studio самостоятельно.
- **GEN-005.** Формат распространения — портативный ZIP; после распаковки не требуются установка Python, Node.js, СУБД или средства разработки.
- **GEN-006.** Обычный запуск через EXE без консольного окна; доступен отдельный диагностический запуск с журналированием.
- **GEN-007.** Основные структурированные данные — JSON-файлы в каталоге программы; SQLite и иная обязательная серверная СУБД не применяются. Медиа и документы — отдельные файлы.
- **GEN-008.** Первый официальный релиз 1.0 содержит весь обязательный функционал настоящего ТЗ. Урeзанный публичный MVP не выпускается.
- **GEN-009.** Внутренние промежуточные сборки допустимы для проверки компонентов; комплексная приёмка проводится после объединения всех подсистем.
- **GEN-010.** Установка обновлений только вручную. Автоматических сетевых проверок и автоматической установки обновлений нет.

## 1.3. Не входят в объём 1.0

Синтез речи (TTS), распознавание речи (STT), голосовой чат, обязательное облако, официальный публичный каталог персонажей, учётные записи нескольких пользователей, удалённый доступ из локальной сети по умолчанию, автозагрузка/автовыгрузка моделей LM Studio, автоматическое обновление программы. Горячие клавиши и командная палитра не являются необходимым способом управления; все действия выполняются через кнопки, меню и формы.

## 1.4. Определения

**Карточка персонажа** — переносимое описание постоянных свойств персонажа. **Состояние персонажа** — изменения в конкретной истории. **Память** — записи об известных персонажам событиях и фактах с источниками. **Мир** — переиспользуемая вселенная с локациями и правилами. **Сценарий** — стартовые условия и необязательные сюжетные конструкции. **История** — независимый экземпляр прохождения. **Сцена** — текущий эпизод истории. **Режиссёр** — скрытая подсистема генерации сюжетных предложений и событий, не подменяющая волю пользователя. **Лорбук** — база знаний о мире и условиях включения записей в контекст.

# 2. Архитектура и технический стек

## 2.1. Утверждённый стек

- **ARCH-001.** Frontend — React + TypeScript, предварительно Vite для сборки статических файлов.
- **ARCH-002.** Backend — Python + FastAPI; один локальный HTTP-сервер обслуживает UI, внутренний API и потоковые события.
- **ARCH-003.** Запуск с loopback-интерфейса `127.0.0.1`; порт выбирается автоматически из доступных или задаётся в настройках. Нельзя без дополнительного явного решения открывать сервис на `0.0.0.0`.
- **ARCH-004.** Browser-клиент не обращается напрямую к файлам данных. Все изменения проходят через backend, проверку схем и сериализованный менеджер хранения.
- **ARCH-005.** Логическая модульность: `core`, `storage`, `characters`, `chat`, `generation`, `prompts`, `memory`, `world`, `director`, `relationships`, `media`, `editor`, `automation`, `plugins`, `diagnostics`.
- **ARCH-006.** Независимость предметной модели от React и от конкретной версии LM Studio. Связь через типизированные API-контракты и адаптер LLM.
- **ARCH-007.** Фоновые работы распределяет единая очередь с приоритетом ответа пользователю, отменой задач, таймаутами и журналом выполнения.
- **ARCH-008.** Событийная шина передаёт изменения истории, памяти, мира, медиа и состояния интерфейсу; события должны иметь идентификаторы и защиту от повторной обработки.

## 2.2. Принцип разделения ответственности

Frontend обеспечивает отображение и ввод, не принимает решений о достоверности фактов мира. Backend исполняет бизнес-правила, собирает промпты и управляет файлами. LM Studio генерирует текст, но не получает необусловленного права менять файлы, вызывать команды ОС или переписывать прошлые события. Для решений, принимаемых на основе ответа модели, применяется схема «предложение → валидация → применение/отклонение → журнал».

## 2.3. Локальные HTTP-интерфейсы

- **API-001.** Версионированный внутренний API `/api/v1/...`, схемы запросов и ответов; ошибки структурированы и локализованы.
- **API-002.** Потоковая выдача токенов, отмена генерации, завершение с фиксацией результата и восстановление после частичного ответа.
- **API-003.** API операций персонажей, историй, памяти, миров, сценариев, медиа, настроек, автоматизации, диагностики и резервных копий.
- **API-004.** Проверка Origin/Host, анти-CSRF для мутирующих запросов, ограничение размера запросов, локальная авторизация с токеном сеанса и безопасными cookie либо эквивалентная схема защиты от соседних сайтов.
- **API-005.** Закрытие вкладки не должно уничтожать сохранённые данные; завершение приложения корректно останавливает задачи и сервер.

# 3. Интерфейс и пользовательский опыт

## 3.1. Основные экраны

- **UI-001.** Главная панель: продолжение недавних историй, библиотека персонажей, сценарии и состояние LM Studio.
- **UI-002.** Визуальный стиль — современный мессенджер, без копирования устаревшей компоновки SillyTavern.
- **UI-003.** Комбинированная навигация с настраиваемыми, сворачиваемыми, перемещаемыми и масштабируемыми панелями; расположение сохраняется.
- **UI-004.** Библиотека персонажей в режиме плиток или списка, с поиском, папками, тегами, фильтрацией и сортировкой.
- **UI-005.** Для каждого чата доступны независимо: мессенджер, литературный режим и визуальная новелла; переключение не изменяет исходные сообщения.
- **UI-006.** Три уровня доступности параметров: простой, расширенный, эксперт; экспертные поля не должны исчезать из сохранённых профилей при переключении.
- **UI-007.** Готовые темы и ручная настройка цветов, шрифтов, размеров, фонов; экономичный режим отключает тяжёлые эффекты.
- **UI-008.** Контекстные боковые панели: персонаж, память, отношения, сюжет, состояние мира, инспектор контекста.
- **UI-009.** Персонализируемые рабочие пространства и режим погружения; видимость панелей и расположение сохраняются отдельно от данных истории.
- **UI-010.** Все основные операции доступны обычными кнопками и пунктами меню; обязательных горячих клавиш или командной палитры нет.
- **UI-011.** Автосохранение редактируемых данных, явная индикация незаписанных изменений и понятное восстановление после сбоя.
- **UI-012.** Доступные состояния: загрузка, пустая библиотека, отсутствие модели, временный сбой, прерванная генерация; ни одно не должно выглядеть как бесконечное зависание.

## 3.2. Ключевые пользовательские сценарии

**UX-01:** распаковать ZIP, запустить EXE, увидеть главный экран и статус LM Studio. **UX-02:** импортировать карточку PNG/JSON и начать новый чат. **UX-03:** создать персонажа в ИИ-мастере, открыть экспертные поля, сохранить. **UX-04:** создать мир и сценарий, запустить независимую историю. **UX-05:** продолжить историю после перезапуска, просмотреть память и события. **UX-06:** открыть сюжетную ветку и вернуться к прежнему варианту без потери другого. **UX-07:** создать изображение сцены при доступном локальном движке. **UX-08:** сформировать литературный документ и экспортировать EPUB. **UX-09:** восстановить историю из резервной копии. Все сценарии подлежат сквозной проверке.

# 4. Персонажи и их карточки

- **CHR-001.** Максимально подробная карточка: имя, описание, характер, биография, мотивация, привычки, страхи, стиль речи, примеры диалогов, стартовый сценарий, приветствия, пользовательские поля и секции.
- **CHR-002.** Два редактора: простой пошаговый мастер и экспертный редактор с полным доступом к полям, подсказкам и проверкам.
- **CHR-003.** Генерация и улучшение карточек через LM Studio: начальная генерация, расширение биографии, примеры реплик, поиск противоречий; результат редактируется до сохранения.
- **CHR-004.** Режим характера задаётся для персонажа: фиксированный, гибкий, развивающийся. Переходы и ограничения должны быть видимы в редакторе.
- **CHR-005.** Эмоции и отношения: автоматические предложения модели, проверяемая история изменений, ручная корректировка и возможность отключения.
- **CHR-006.** Поддержка портретов, набора выражений, костюмов, анимаций, индивидуальных фонов и привязки медиа к состояниям.
- **CHR-007.** Групповые сцены: несколько героев, выбор очередности реплик, появление и уход, диалоги NPC друг с другом, контроль присутствия в сцене.
- **CHR-008.** Несколько альтернативных приветствий, стартовых ситуаций, сценариев и пресетов.
- **CHR-009.** Один персонаж может участвовать во множестве независимых историй; память и отношения каждого прохождения изолированы. Выборочный перенос событий — явная отдельная операция.
- **CHR-010.** Только собственная локальная библиотека без встроенного публичного каталога; ручной импорт карточек сохраняется.
- **CHR-011.** Контроль качества ответов: предупреждение о выходе из роли, повторах, нарушениях формата, выборочная регенерация с ограничением попыток и сохранением истории решений.
- **CHR-012.** Пользователь свободно пишет от своего имени; обязательный конструктор собственной игровой персоны не вводится. ИИ не пишет за пользователя без отдельного запроса.

## 4.1. Совместимость

- **COMP-001.** Импорт существующих карт V1/V2/V3 в JSON и PNG при соответствии документированным спецификациям.
- **COMP-002.** Экспорт в поддерживаемые версии формата; любые поля, неподдерживаемые целевым форматом, перечисляются в отчёте о совместимости.
- **COMP-003.** Неизвестные расширения и метаданные сохраняются при импорте и последующем экспорте, если технически возможно; не допускается молчаливая потеря ценных полей.
- **COMP-004.** Стандартная карточка и расширенные данные «Таверны» разделены. Для полного сохранения расширений предусмотрен собственный пакетный формат.
- **COMP-005.** Импорт истории чата и типовых лорбуков SillyTavern — отдельные адаптеры с проверкой форматов и пользовательским предпросмотром.
- **COMP-006.** Проверка совместимости на наборе реальных контрольных карточек, не только на искусственных примерах; никаких обещаний абсолютной совместимости с неизвестными сторонними расширениями.

# 5. Чаты, сюжеты, миры и сценарии

## 5.1. Работа с диалогами

- **CHAT-001.** Потоковый вывод текста, остановка, продолжение, повтор ответа, редактирование сообщения и удаление с предупреждением о последствиях.
- **CHAT-002.** Несколько вариантов ответа (swipes), сравнение вариантов, частичная регенерация при технической поддержке операции, сохранение выбранной ветви.
- **CHAT-003.** Неразрушающее дерево ветвлений, главы, закладки, поиск по истории, карта сюжетных связей, контрольные точки.
- **CHAT-004.** В истории сохраняются текст, автор, время, версия, модель, профиль промпта, привязанные события/файлы и связи с исходными сообщениями.
- **CHAT-005.** Для групповых чатов — список участников, состояния присутствия, выбор говорящего и защита от случайной генерации от лица пользователя.

## 5.2. Модель мира

- **WORLD-001.** Иерархия «мир → сценарий → история → сцена». Мир и сценарий переиспользуются, истории изолированы.
- **WORLD-002.** Конструктор мира: география, места, фракции, история, культура, правила, ресурсы, связи между сущностями и лорбук.
- **WORLD-003.** ИИ-мастер создания и расширения мира/сценария с предварительным просмотром и подтверждением структурированных результатов.
- **WORLD-004.** Живой мир: NPC и фракции действуют за пределами текущей сцены; изменения рассчитываются по игровому времени и событиям, а не обязательной бесконечной фоновой генерацией.
- **WORLD-005.** Гибридная система событий: свободные предложения LLM + детерминированные условия, триггеры, последствия и ручное вмешательство пользователя.
- **WORLD-006.** Календарь, время суток, временные пропуски, перемещение, текущие локации, редактирование состояния мира пользователем.
- **WORLD-007.** Причины, последствия, незавершённые линии, персонажи и события связываются ссылками; изменения проходят проверку на логические конфликты.
- **WORLD-008.** Опциональные игровые модули: инвентарь, характеристики, навыки, кубики, экономика, конфликты, случайные события. Обычный литературный чат работает без них.
- **WORLD-009.** Полный конструктор сценариев: ручное создание, шаблоны, ИИ-мастер, генератор случайного старта, сохранение собственных сценариев.

## 5.3. Режиссёр и автономность NPC

- **DIR-001.** Режиссёр автоматически предлагает повороты, конфликты и возможности для свободного развития истории; его работа скрыта от художественного текста.
- **DIR-002.** Активные NPC проявляют инициативу и принимают самостоятельные решения в пределах своих знаний, характера, положения и состояния мира.
- **DIR-003.** Режиссёр не должен насильно возвращать пользователя на предусмотренный маршрут и не может без отдельной команды писать реплики или принимать решения за пользователя.
- **DIR-004.** Предложения режиссёра, подтверждённые изменения и отвергнутые действия журналируются для диагностики, без обязательного отображения пользователю в чате.
- **DIR-005.** События, необходимые для следующей сцены, подготавливаются до ответа; долгие аналитические работы можно выполнять после ответа.
- **DIR-006.** Реальные и субъективные знания персонажей разделены; ложь, слухи и ошибочные убеждения хранятся как субъективные факты.

# 6. Память, контекст, отношения и поиск

## 6.1. Уровни памяти

- **MEM-001.** Шесть логических уровней: оперативная, эпизодическая, личная память NPC, отношения, состояние мира и сюжетная память.
- **MEM-002.** Автоматическое извлечение значимых фактов через модель с ручным просмотром, редактированием, закреплением и удалением.
- **MEM-003.** Индивидуальные знания NPC: прямые наблюдения, полученные сведения, слухи, заблуждения и тайны с указанием источника и степени уверенности.
- **MEM-004.** Настраиваемое забывание: значимые факты закрепляются; менее важные уходят в архив или теряют приоритет, но исходные данные не уничтожаются автоматически.
- **MEM-005.** Гибридные отношения: текстовое описание, числовые показатели, важные эпизоды и история изменения отношений.
- **MEM-006.** Хронология глав, временная шкала, причины/следствия, контрольные точки, сводки эпизодов.
- **MEM-007.** Полный пользовательский редактор памяти, источники, версия, история изменений, экспорт и импорт.

## 6.2. Контекстный менеджер

- **CTX-001.** Модульная сборка системных инструкций, карточек, сцены, лорбука, текущего состояния, последних сообщений и релевантных воспоминаний.
- **CTX-002.** Автоматическое распределение бюджета токенов с ручными лимитами и обязательным резервом для ответа.
- **CTX-003.** При нехватке контекста — ступенчатое сокращение: приоритеты, извлечение релевантных фактов, сводки, предупреждения; закреплённые факты защищены политикой приоритетов, но ограничения модели не скрываются.
- **CTX-004.** Инспектор показывает итоговый промпт, состав, оценку токенов, активированные/исключённые знания и причины отбора.
- **CTX-005.** Состав промпта и выбранные источники протоколируются при необходимости диагностики с учётом приватности локальных журналов.
- **CTX-006.** Проверки конфликтов памяти: версии фактов, связь с исходными сообщениями, обнаружение неоднозначностей и пользовательское разрешение.
- **CTX-007.** Гибридный поиск: полнотекстовый и смысловой, фильтры по сущности, времени, локации, типу записи и источнику.
- **CTX-008.** Векторные представления кэшируются; при отключении или отсутствии embedding-модели сохраняется текстовый поиск.
- **CTX-009.** Вспомогательные операции запускаются адаптивно по событиям; основной диалог имеет приоритет.

# 7. LM Studio и генерация

- **LLM-001.** Автопоиск локального сервера с возможностью ручной настройки адреса и порта, проверки соединения и отображения ошибок.
- **LLM-002.** Выбор из доступных в LM Studio моделей; операции загрузки, выгрузки и скачивания моделей остаются только в LM Studio.
- **LLM-003.** Одна модель по умолчанию; опциональное распределение основной и вспомогательных ролей между несколькими уже загруженными моделями при достаточных ресурсах.
- **LLM-004.** Готовые профили генерации и экспертный режим с параметрами, реально поддерживаемыми текущим API и моделью.
- **LLM-005.** Настройки модели отдельно для чатов, персонажей и служебных задач, понятные правила приоритета и наследования.
- **LLM-006.** Автоматическое и ручное управление контекстом, предупреждения о переполнении, диагностика оценок токенов.
- **LLM-007.** Полный набор действий с ответами: стоп, повтор, продолжение, редактирование, варианты, частичная регенерация и сравнение.
- **LLM-008.** Модульный конструктор системных промптов, шаблоны, условные секции, порядок вставки, просмотр итогового запроса.
- **LLM-009.** Обработка reasoning-контента с учётом реально поддерживаемых моделью каналов; отделение служебного вывода от финального текста, настройка отображения и фильтрации.
- **LLM-010.** Ошибки соединения, таймауты, прерывание, ограниченные повторные попытки с защитой от дублирования сообщений и сохранением незавершённого ответа.
- **LLM-011.** Мониторинг: время до первого токена, общая длительность, токены в секунду, использование контекста, ошибки, доступность модели.
- **LLM-012.** Три профиля производительности: экономичный, сбалансированный, максимальное качество; каждый чат может выбрать профиль независимо.
- **LLM-013.** Проверка доступности advanced-функций (structured output, embeddings, tool calling) перед использованием, безопасное ухудшение возможностей при их отсутствии.
- **LLM-014.** Адаптер API отделён от логики приложения, чтобы обновления LM Studio не требовали переделки доменных моделей.

## 7.1. Целевая тестовая конфигурация

Windows, Intel Core i5-11400F, NVIDIA GeForce RTX 5070 (12 ГБ VRAM), 32 ГБ RAM, `dolphin-2.9.3-mistral-nemo-12b.Q5_K_M.gguf`. Стартовые испытания: контекст 8192, затем 16384 токена, резерв ответа 1024–2048 токенов; конкретные оптимальные параметры определяются измерениями, не гарантируются заранее. # 11. Файловое JSON-хранилище

## 11.1. Принципы

- **STOR-001.** Структурированные доменные записи — версионированные JSON-документы, медиа — отдельные файлы, без SQLite.
- **STOR-002.** Каталоги `data/characters`, `data/chats`, `data/worlds`, `data/scenarios`, `data/memory`, `data/relationships`, `data/config`, `data/indexes`, `media`, `library`, `plugins`, `backups`, `logs`.
- **STOR-003.** Все сущности имеют UUID; ссылки используют идентификаторы, не имена файлов или персонажей.
- **STOR-004.** Большие чаты сегментируются на ограниченные по размеру JSON-файлы с метаданными и связями; запрещена полная перезапись гигантского чата при добавлении одной реплики.
- **STOR-005.** Запись одиночного файла: временный файл на том же томе, валидация, сброс данных по выбранной политике, атомарная замена там, где гарантирована ОС и файловой системой.
- **STOR-006.** Для многофайловых операций: журнал транзакций/намерений, согласованный порядок публикации и восстановление после сбоя; атомарность одного файла не выдаётся за атомарность нескольких.
- **STOR-007.** Одновременные изменения сериализуются серверным менеджером, применяются проверки версий и обнаружение конфликтов. Несколько вкладок браузера не должны бесконтрольно перетирать данные.
- **STOR-008.** Структура JSON имеет `schema_version`; миграции версионируются, тестируются, ведут журнал и не удаляют исходные данные до успешного завершения.
- **STOR-009.** Текстовые и векторные поисковые индексы являются производными, могут пересоздаваться из исходных данных.
- **STOR-010.** Отсутствие или повреждение одного необязательного ресурса не должно делать недоступной всю библиотеку.
- **STOR-011.** Данные и настройки находятся в каталоге переносимой программы; абсолютные пути не должны ломать перенос на другой диск. Допускаются только явно настроенные внешние каталоги, например резервный.

## 11.2. Примерная схема основных сущностей

| Сущность | Обязательные свойства | Связи |
|---|---|---|
| Character | id, schema_version, name, card_fields, timestamps | media, presets |
| World | id, name, rules, entities, lorebook | locations, factions |
| Scenario | id, world_id, entry_state, conditions | characters, templates |
| Story | id, scenario_id, active_branch, state_version | scenes, messages |
| Message | id, branch_id, author_id, text, created_at | versions, events |
| MemoryFact | id, proposition, source_ids, confidence, scope | npc, story, event |
| Event | id, story_id, game_time, cause_ids, effects | scenes, states |
| Relationship | id, parties, narrative, measures, history | memories, story |
| MediaAsset | id, relative_path, type, checksum | character, scene |
| AutomationRule | id, trigger, conditions, actions, grants | log |

Это логическая схема, а не окончательная JSON Schema. Полный каталог обязательных/опциональных полей и миграций выпускается при разработке компонента `storage`.

## 11.3. Резервирование

- **BACK-001.** Автосохранение после значимых изменений и сообщений, с индикацией результата.
- **BACK-002.** Регулярные автоматические локальные копии, согласованные между JSON, медиа, настройками и метаданными.
- **BACK-003.** Проверка целостности копии по манифесту и контрольным суммам; обнаружение неполных архивов.
- **BACK-004.** Настраиваемая политика хранения. Начальная рекомендация: 7 ежедневных и 4 недельных копии; фактическая частота — при запущенной программе.
- **BACK-005.** Восстановление из копии через мастер с предварительным просмотром, проверкой совместимости версии и отдельной контрольной копией текущего состояния.
- **BACK-006.** Дополнительный резервный каталог на ином диске может быть назначен пользователем; копии в одном каталоге с программой не защищают от потери всего диска.
- **BACK-007.** Перед ручным обновлением/миграцией создаётся отдельная контрольная резервная копия.

# 12. Безопасность, приватность, отказоустойчивость

- **SEC-001.** По умолчанию только loopback HTTP; доступ извне не открывается.
- **SEC-002.** Защита от произвольных путей (`..`, симлинки/переходы за корень), zip-slip, недопустимых расширений, больших файлов и повреждённых медиа.
- **SEC-003.** Импортированные описания, промпты и документы считаются недоверенным текстом, не исполняются как системные инструкции для backend или команды ОС.
- **SEC-004.** Секреты и токены локальных интеграций не записываются в открытые диагностические журналы.
- **SEC-005.** HTML/Markdown-предпросмотр очищается от потенциально опасных скриптов и активного содержимого; выдаются строгие заголовки безопасности.
- **SEC-006.** Плагины и макросы работают по модели минимально необходимых полномочий; опасные операции требуют видимого подтверждения.
- **SEC-007.** Очередь задач ограничена по размеру и ресурсам; таймауты, отмена, повтор с идемпотентностью и корректное завершение.
- **SEC-008.** После перезапуска выполняется проверка незавершённых транзакций, целостности базовых данных и возможности восстановления.
- **SEC-009.** Система создаёт диагностический архив без автоматической передачи данных наружу, с возможностью исключить содержимое историй и личных материалов.
- **SEC-010.** Никакие обновления приложения не проверяются и не устанавливаются автоматически.

# 13. Производительность и качественные требования

## 13.1. Общие требования

- **NFR-001.** Интерфейс не должен блокироваться синхронной генерацией LLM, импортом медиа, индексированием или резервированием.
- **NFR-002.** Основной ответ LLM имеет преимущество над необязательными задачами памяти и режиссёра.
- **NFR-003.** Большие истории загружаются постранично/виртуализированно; не допускается загрузка всех сообщений в DOM одновременно.
- **NFR-004.** При отсутствии LM Studio сохраняется доступ к библиотеке, редакторам, сохранённым историям и настройкам; генерация явно недоступна.
- **NFR-005.** При отсутствии генератора изображений сохраняются импорт, галерея и настройка визуальных ресурсов.
- **NFR-006.** Экономичный режим отключает тяжёлые визуальные эффекты и сокращает вспомогательные ИИ-операции, но не удаляет функции и данные.
- **NFR-007.** Пороговые показатели времени реакции и нагрузки устанавливаются после измерения на целевой конфигурации; значения без испытаний не должны объявляться гарантией.

## 13.2. Контрольные профили

| Профиль | Приоритет | Поведение |
|---|---|---|
| Экономичный | Минимальная задержка | Дополнительные ИИ-задачи редко или после паузы |
| Сбалансированный | Ответ + согласованность | Адаптивная память и события, ограниченная очередь |
| Максимальное качество | Детальность | Дополнительные проверки и подробная обработка с видимой задержкой |

# 14. Сборка, переносимость, обновление и документация

- **REL-001.** Поставка одним ZIP с готовыми исполняемыми файлами и статическим веб-интерфейсом; установщик Windows не требуется.
- **REL-002.** `Taverna.exe` запускает сервер, открывает браузер и закрывает собственные процессы по завершении; `Taverna-Diagnostics.exe` предоставляет режим диагностики.
- **REL-003.** Данные, плагины, мультимедиа, логи и резервные копии по умолчанию расположены в переносимой папке приложения.
- **REL-004.** Программа не зависит от установленного глобально Python/Node.js и не должна менять системные переменные или реестр без необходимости.
- **REL-005.** Ручное обновление: закрытие приложения → проверка архива → резервная копия → замена программных файлов → миграция данных → проверка запуска; при ошибке восстановление.
- **REL-006.** Полный комплект документов: руководство пользователя, техническая архитектура, формат данных, документация API и плагинов, история версий, результаты испытаний, встроенная справка.
- **REL-007.** Лицензии сторонних библиотек и включённых ресурсов проверяются и включаются в поставку; нельзя без проверки переносить чужие изображения, музыку или программный код.

# 18. Трассируемость, изменения ТЗ и открытые инженерные вопросы

## 18.1. Трассируемость

Каждое требование имеет постоянный идентификатор. При реализации для него указываются исходный этап согласования, модуль-владелец, версия схемы/API, набор тестов, результат и ссылка на документацию. Требования с неуспешными тестами блокируют окончательную приёмку, если не сняты отдельным решением владельца проекта.

## 18.2. Предварительные инженерные вопросы без изменения концепции

1. Окончательные JSON Schema и размер сегмента сообщений.
2. Выбор формата и реализации индекса смыслового поиска при отсутствии обязательной СУБД.
3. Способ безопасного запуска недоверенных плагинов на Windows и перечень разрешений.
4. Адаптер локальной генерации изображений, ограничения памяти GPU и типы поддерживаемых движков.
5. Поддерживаемые версии Windows, список браузеров и политики совместимости.
6. Конкретные численные пороги отзывчивости после измерений на целевом ПК.
7. Точная структура собственных пакетов экспорта персонажа, истории и мира.
8. Система подписи и проверки целостности релизных архивов.

Перечисленные детали выбираются при техническом проектировании; они не дают оснований исключать утверждённые функции. При выявлении несовместимых требований оформляется запрос на изменение ТЗ, а не молчаливое упрощение.

## 18.3. Контроль изменений

Изменение требований фиксируется по номеру, дате, формулировке, причине, затронутым модулям, миграциям, тестам и решению владельца. Новая редакция ТЗ должна сохранять историю изменений. Текущая редакция не разрешает запуск разработки.

# 19. Итоговый комплект релиза

Поставка 1.0 должна содержать: основной `Taverna.exe`, диагностический запуск, frontend/backend со всеми зависимостями, начальную структуру каталогов, файлы схем/миграций, полный русскоязычный интерфейс, руководство пользователя, документацию разработчика, руководство по плагинам, описание API, историю изменений, лицензии сторонних компонентов, тестовый отчёт и механизм автоматического резервирования/ручного восстановления. Сама модель LM Studio и веса внешних генераторов изображений не включаются автоматически в ZIP, если отдельно не согласована их законная поставка.

# 20. Условия утверждения документа

Это единое ТЗ объединяет решения этапов 1–8. Приоритетны явные пользовательские требования: Windows, локальное веб-приложение, LM Studio, исключительно JSON для структурированных данных, portable ZIP, один пользователь, полный первый релиз, ручные обновления, отсутствие TTS/STT, обычные кнопки. Инженерные предложения, не закреплённые пользователем отдельно (например, конкретная политика хранения копий или выбор индексной библиотеки), подлежат технической проверке и уточнению. **До отдельной явной команды программирование не начинается.**
