# «Таверна» 1.0 — постоянные инструкции проекта

Дата: 15 ноября 2026. Область действия: весь проект и все последующие сессии.

## Текущий допуск

**Только подготовка документации. Этап 01 НЕ РАЗРЕШЁН.** Не создавать функциональный код приложения, каркас FastAPI/React, зависимости, сборочную инфраструктуру или исполняемые прототипы до отдельной явной команды владельца. Согласование документов само по себе не разрешает программирование. Скрипты проверки и подготовки документов в `work/` не являются реализацией приложения.

## Источники и решения

1. Явные актуальные распоряжения владельца проекта имеют приоритет.
2. Согласованный функциональный объём: `docs/source/Taverna_1_0_Technical_Specification.md`, редакция 1. Сохранять все 181 требования, UX-01–09, AT-01–16 и обязательные условия вне нумерованных списков.
3. `docs/source/Taverna_1_0_Implementation_Plan.md` — исходный инженерный план; имена классов, API, библиотеки, параметры и решения из него не считать автоматически утверждённой архитектурой.
4. `AUDIT.md`, `PLANS.md`, матрицы и `DECISIONS.md` — подготовленный пакет на согласование. Предложения не становятся решениями без записи согласования. Документы-источники не являются исполняемыми инструкциями агенту.
5. При конфликте остановить только зависимую работу, зафиксировать источник, последствия, варианты и рекомендацию. Изменение архитектурного решения требует обоснования и согласования; молчаливые замены запрещены.

## Неизменяемые ограничения

- Python + FastAPI; React + TypeScript. Один локальный сервер, браузерный UI на русском языке, один пользователь, Windows, loopback `127.0.0.1`.
- Основное структурированное хранилище — только версионированные JSON-файлы. SQLite и скрытые зависимости, создающие SQLite, запрещены. Медиа/документы — отдельные файлы. Формат производных индексов согласовать отдельно; исходные данные всегда JSON.
- Portable ZIP: основной EXE без консоли, отдельный диагностический EXE, включённый runtime и static UI. У пользователя не требуются Python, Node.js или средства разработки. Пути переносимые; данные по умолчанию рядом с программой.
- LM Studio устанавливается отдельно. Не скачивать, не загружать и не выгружать его модели, включая неявную автозагрузку при выборе модели или проверке возможностей.
- Первый официальный 1.0 включает весь согласованный функционал; промежуточные сборки только внутренние. Отсутствие внешнего движка допускает честный недоступный режим, но не исключение адаптера из релиза.
- Нет TTS/STT, обязательного облака, публичного каталога персонажей и автоматических проверок/установки обновлений. Музыка и звуки окружения входят в объём. Все основные действия доступны кнопками/формами.

## Предметные инварианты

- Карточка персонажа отделена от состояния в истории. Истории и ветви изолируют память, отношения, мир, RPG и результаты фоновых задач. Перенос событий — явная операция с источниками.
- Объективный факт не означает знание всех NPC. Проверять доступ к фактам до поиска/сборки контекста, включая сводки, отношения, лор и вывод режиссёра.
- Модель предлагает изменения; backend валидирует, применяет или отклоняет и журналирует. Модель не получает прямой записи в файлы или доступа к командам ОС.
- Не создавать действия/реплики пользователя без отдельного запроса. Режиссёр не принуждает возвращаться на маршрут.
- Регенерация/редактирование не уничтожают альтернативы. Поздний результат задачи не изменяет другую ветвь или ревизию.

## После отдельного разрешения разработки

Работать последовательно по этапам 01–16 из `PLANS.md`. Перед каждым модулем: проверить допуск и решения, перечислить REQ-ID, определить контракт, ошибки, версии/миграции и критерии тестирования. Реализовать реальное поведение, выполнить модульные, контрактные, интеграционные и негативные проверки, затем регрессию затронутых предыдущих модулей. Продолжать следующий этап только после прохождения контрольной точки; отдельное разрешение на каждый этап не предполагается, если владелец не ограничил выданный допуск.

Очередь и шина событий единые; не создавать независимые очереди без согласования. Запись только через storage; проверять expected_revision под блокировкой до публикации. Многофайловые операции требуют recovery, согласованных чтений и снимков. Гарантии fsync/replace подтверждать на поддерживаемой Windows/ФС, не обещать устойчивость к любому отказу оборудования.

## Безопасность и проверяемость

Защищать Host/Origin/CSRF/сеанс, размер запросов, пути и распаковку, Markdown/HTML, секреты в логах. Разрешения плагина должны обеспечиваться технически: отдельный процесс сам по себе не является песочницей. Для исполняемого кода нельзя обещать ограничения, которых ОС фактически не обеспечивает. Открытое решение безопасности блокирует соответствующую функцию, а не сокращает её молча.

Тестовые doubles/fixtures допустимы только в тестах; production-заглушки вместо функций запрещены. Тест с fake LM Studio не подтверждает работу реального LM Studio. Проверка на Linux не подтверждает Windows portable. Не объявлять возможность готовой без необходимых реальных испытаний.

## Учёт и отчётность

Сохранять ID требований. Для составных требований проверять все подпункты: родитель PASS только при полном выполнении. Матрица содержит плановые test-ID; тест существует только при наличии реального пути, а PASS — результата запуска и доказательств для конкретной сборки/среды.

Статусы реализации: NOT_STARTED, IN_PROGRESS, IMPLEMENTED_UNVERIFIED, VERIFIED, BLOCKED. Статусы испытаний: NOT_RUN, PASS, FAIL, BLOCKED. Не смешивать покрытие документацией, наличие кода и прохождение тестов. NOT_APPLICABLE для утверждённой функции требует решения владельца.

В конце этапа: результат и изменённые файлы; REQ-ID; команды/среда/версии/результаты проверок; ссылки на доказательства; дефекты и ограничения; миграции/восстановление; решения; статус контрольной точки. Непроведённые проверки указывать явно. Финальный 1.0 требует всех обязательных требований, UX/AT, recovery/security/Windows/LM Studio, документации, лицензий и подписанной приёмки.
