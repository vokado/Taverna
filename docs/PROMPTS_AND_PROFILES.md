# Профили, контекст и проверка ответа

Этап 07. REQ-ID: CTX-001–005, LLM-004/006/008/009/011/012, CHR-011, CHAT-004, UI-006, SEC-003/004. Составные CTX-001/003 требуют продолжения в 08–10; реальные LLM/производительность — аппаратных испытаний. Наличие этого документа не означает PASS требований.

Контракт v1: ProfileSettings (экспорт JSON Schema), generation_profile envelope v1 с `name/patch/builtin`, profile_binding v1, generation_context v1. API `/profiles`, `/profiles/{id}`, `/profiles/bindings`, `/profiles/resolve`, `/stories/{id}/context-preview`, `/contexts/{id}`. Мутации защищены сеансом/CSRF и expected_revision. Ошибки: invalid_profile, invalid_scope, profile_missing, branch_conflict/generation_stale, context_configuration, pinned_block_overflow, pinned_context_overflow, answer_quality_rejected. Данные только через JsonStore; новая версия формата не заменяет старые истории, миграция имеющихся сообщений не нужна. Три встроенных профиля создаются однократно; последующий запуск не перезаписывает изменения владельца.

Наследование — частичные патчи: базовый сбалансированный → общий → служебная роль → персонаж → история/группа → профиль задачи → явные параметры запроса. Объекты объединяются рекурсивно, массивы заменяются целиком. Все профили/назначения читаются под одним storage view; цепочка ID/revision записывается вместе с фактически выбранными настройками. Экспертные extras сохраняются, но произвольные имена параметров не отправляются движку. Общие параметры и независимые назначения истории доступны в редакторе; выбор профиля конкретного запроса доступен в чате. Автоматического выбора другой модели при недоступности нет. Модель берётся из явного выбора или профиля и проверяется как уже загруженный экземпляр.

Параметры транспорта: max_tokens, temperature, top_p, frequency_penalty, presence_penalty, seed и stop; границы и типы проверяются до отправки. Соответствие конкретной версии LM Studio/модели проверяется отдельно: тестовый транспорт не является доказательством живой совместимости. Профили производительности — наборы параметров для испытаний, а не обещанные скорость/VRAM или выгрузка других моделей.

Сборщик использует собственную snapshot-карточку NPC, видимую ему историю, публичные координаты сцены, явно доступную память/отношения и карточный лорбук. Другие приватные состояния/world truth целиком не сериализуются. Память/отношения требуют совпадения story/branch и knower_ids; неполные/чужие записи исключаются до включения. Сообщения доступны по present_ids или собственному авторству. creator_notes не включаются. Системное поле карты поддерживает `{{original}}`; доступны одношаговые макросы char/user/content/original. Условия — типизированные равенства group/has_world/has_memory/performance/role, без eval, Python или доступа к атрибутам. Порядок блоков хранится в профиле; неизменная инструкция приложения не даёт модели файловых прав и не разрешает реплики за пользователя.

Сейчас карточный лор поддерживает enabled/constant/keys. Полный мировой лорбук и его импорт, retrieval/сводки, состояния режиссёра/RPG интегрируются в 08–11. Их отсутствие не обозначается выполненным требованием. Сводки не заменяются выдуманными шаблонными строками.

Оценка tokens: balanced = ceil(UTF-8 bytes/2), conservative = UTF-8 bytes, плюс 24 на сообщение. Оба метода приблизительные, не нативные токенизаторы. Фактические usage берутся только из ответа движка. Автоматическое окно ограничивается меньшим из профиля и известного loaded context_length; ручное превышение загруженного окна запрещено. Из окна вычитаются обязательный резерв ответа и safety margin. Внутри бюджетов блоков защищённые элементы резервируются первыми, затем выбираются новые незакреплённые. При общем дефиците исключаются низкоприоритетные и более ранние элементы. Закреплённые блоки/факты и последнее видимое сообщение не обрезаются: если они превышают ручной бюджет блока или остаток окна, запрос останавливается с объяснением. Точные аппаратные пределы не скрываются приблизительной оценкой.

Предпросмотр ничего не сохраняет и явно не подтверждает окно движка. Фактический trace фиксируется перед inference и связан с событием задачи/итоговым сообщением; последующий отказ движка остаётся в журнале. Trace содержит messages, selected/excluded с причинами, оценку, лимиты, профили/ревизии и параметры. request_sha256 покрывает канонические model_id/parameters/messages (не сетевые заголовки и framing SSE). Обычные диагностические текстовые логи не содержат промпт. По умолчанию полный trace сохраняется локально для инспектора; при save_context=false messages/selected/настройки профиля не сохраняются, остаются метаданные, цепочка назначений и хеш. Инспектор честно показывает full_context_saved; полный диагностический снимок при таком режиме не сохраняется. Это настройка trace, а не удаления исходных данных: входные сообщения служебной задачи, история чата и результаты остаются в своём журнале для восстановления. Тексты дельт/рассуждений в истории задач сохраняются отдельно для восстановления ответа.

Проверка качества — проверяемые эвристики: пустота, сходство с последними тремя собственными репликами (нормализация и первые 8192 символа), явные маркеры выхода из роли/реплик пользователя, JSON либо оформление диалога. Это не доказательство смысловой правильности или отсутствия галлюцинаций. Режимы warn/retry/reject; retry_on выбирает классы повторов, максимум 1–3 попытки, по умолчанию warn. Каждая попытка и решение журналируются. Повтор использует настоящий adapter, принятый ответ записывается один раз с прежним branch CAS. Отклонённый ответ не добавляется автоматически; явное применение сохранённого текста остаётся решением пользователя. attempt_started отделяет альтернативы в UI и при восстановлении partial. Рассуждения отдельного поддержанного канала не становятся текстом реплики; отображение можно включить явно, профиль задаёт начальное значение. Извлечение скрытых reasoning из обычного текста не выдумывается.

Критерии проверки: tests/test_profiles_prompts.py плюс генерация/чат/безопасность предыдущих этапов; браузерный profiles.spec.ts создаёт/назначает профиль, проверяет наследование, реальный предпросмотр и перезагрузку. MockTransport используется только в тестах. Аппаратные проверки: три профиля на Dolphin Nemo Q5_K_M/RTX5070, точность оценок относительно actual usage, реальные reasoning-каналы и ответы с контролем роли/повторов/формата — BLOCKED до доступа к целевой системе.
