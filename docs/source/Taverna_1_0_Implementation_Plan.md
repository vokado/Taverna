# 1. Исполнительное резюме

«Таверна» — русскоязычное однопользовательское Windows-приложение с локальным веб-интерфейсом. Исполняемый файл без консоли запускает локальный сервер Python/FastAPI и открывает React/TypeScript в браузере. Пользователь отдельно запускает и загружает модели в LM Studio. Все основные структурированные данные хранятся в **JSON-файлах в папке программы**, мультимедиа — отдельными файлами. SQLite, удалённый сервер и обязательное облако исключены.

План включает 16 последовательных внутренних этапов, полностью согласованных с ТЗ. Каждому этапу назначаются результаты, файловые компоненты, классы и публичные внутренние API, зависимости, автоматические проверки и критерий завершения. **Полная интеграционная приёмка выполняется после реализации всех модулей**; во время разработки обязательно выполняются локальные тесты компонентов и контрактов. Публикуется только один полный выпуск 1.0.

# 2. Схема выполнения и границы процессов

1. **Запуск:** `Taverna.exe` проверяет доступность каталога данных, берёт эксклюзивный lock на один серверный процесс, запускает локальный FastAPI и открывает страницу по loopback-адресу.
2. **Frontend:** React управляет представлением, состояниями UI, формами и потоковой визуализацией; не имеет прямого доступа к дисковым JSON.
3. **Backend:** FastAPI предоставляет `/api/v1/`, выполняет валидацию, сериализацию транзакций, событийные правила и подготовку промптов.
4. **Хранилище:** файл-ориентированный transactional JSON store хранит исходные сущности, версии, сегменты сообщений и журнал операций; индексы только производные.
5. **LLM:** OpenAI-совместимый Chat Completions API LM Studio для ответов и дополнительный read-only native API для обнаружения загруженных моделей. Все обращения выполняются через backend-адаптер.
6. **Изображения:** отдельный локальный генератор по подключаемому адаптеру; без автоустановки и автоуправления моделями LM Studio.
7. **Фоновые задачи:** планировщик с приоритетами, лимитом ресурсов, устойчивым журналом и идемпотентностью. Экономичный режим снижает активность дополнительных задач, но не удаляет функций.
8. **Плагины:** декларируемые разрешения; безопасные декларативные сценарии и отдельно оговорённые доверенные исполняемые расширения.

## 2.1. Границы доверия

- Недоверенное содержимое: карточки, лорбуки, изображения, Markdown/HTML, EPUB, файлы импорта, ответы LLM, manifest плагинов.
- Backend единолично разрешает запись в папку данных и применение изменений мира/памяти. Модель отдаёт **предложения**, а не команды ОС.
- Пользовательские материалы не передаются в интернет автоматически; локальные HTTP-вызовы ограничиваются явно разрешёнными адресами и ресурсами.
- Реальные «права на API» защищены loopback, Host/Origin/CSRF, случайным токеном сеанса, ограничением payload и строгой проверкой путей.
- Python-плагин, исполненный с теми же правами Windows, невозможно надёжно ограничить одним текстовым manifest. Для недоверенных сценариев только декларативный DSL или отдельная подтверждённая ОС-изоляция; доверенный код имеет явную маркировку риска.

## 2.2. Жизненный цикл приложения

| Состояние | Действия и требования |
|---|---|
| STARTING | Lock, проверка дерева, recovery журнала, диагностика JSON Schema, запуск HTTP, открытие браузера |
| READY | UI/локальные данные доступны независимо от LM Studio |
| MODEL_OFFLINE | Чтение и редактирование работают; генерация недоступна с понятной подсказкой |
| GENERATING | Запись черновика ответа, поток чанков, отмена и commit завершения |
| BACKGROUND | Приоритетная очередь память/режиссёр/индекс/копии |
| DEGRADED | Повреждённый необязательный ресурс изолирован; предупреждение и восстановление |
| SHUTTING_DOWN | Отмена/дозавершение задач, flush, закрытие lock; LM Studio остаётся включённым |

# 4. Сквозные контракты данных и API

## 4.1. Общие поля каждой сущности

| Поле | Тип / смысл |
|---|---|
| `id` | UUID, стабильный независимо от имени |
| `schema_version` | целое число версии JSON Schema |
| `revision` | монотонная версия записи для конкурентного изменения |
| `created_at`, `updated_at` | UTC ISO 8601; игровое время отдельно |
| `origin` | создано вручную / импортировано / предложено моделью |
| `provenance` | список источников; для фактов обязательно |
| `extensions` | пространство имён для добавочных данных и сохранения неизвестных полей |

Текстовые данные — UTF-8; сериализация стабильная, schema_version обязательна. Время мира не заменяет timestamp файла. Ссылки — только по ID с проверкой существования и разрешённой области видимости.

## 4.2. Документированная транзакция JSON

**Операции одного файла:** подготовить валидный объект → записать временный файл на том же диске → fsync согласно политике → выполнить атомарную замену, когда поддерживается → проверить revision → зарегистрировать завершение. 

**Многофайловая операция:** создать `transaction_id`, manifest с перечислением участвующих файлов, их предыдущих ревизий и контрольных сумм → записать новые версии в staging → зафиксировать commit-маркер → опубликовать новые версии в согласованном порядке → отметить complete → пересчитать производные индексы. При запуске recovery различает подготовленную, зафиксированную и завершённую транзакции. Прежние файлы не уничтожаются до завершения гарантий восстановления.

Должны быть тесты внезапного завершения процесса после каждого критического шага, нехватки места и ошибки прав. Блокировка одного процесса защищает от двух серверов; оптимистические revision защищают от перезаписи двумя вкладками. Автоматические бэкапы получают согласованный снимок по generation/commit_id.

## 4.3. Структура длинной истории

```text
data/chats/<story_uuid>/
  story.json                 # мир/сценарий/активная ветвь/ревизия
  branches.json              # дерево вариантов и головные сообщения
  messages/000001.json      # сегмент сообщений
  messages/000002.json
  scenes/<scene_uuid>.json
  state/state.json           # состояние персонажей и мира
  revisions/                # выбранные контрольные точки
```

Сегмент — ограниченный по размеру документ; конкретный порог выбирается измерениями (предварительный кандидат: 128–512 сообщений или несколько мегабайт, что наступит раньше). Редактирование сообщения создаёт новую ревизию/ветвь, а не разрушает уже опубликованный вариант. Удаление и очистка требуют явной процедуры безопасного garbage collection после проверки ссылок.

## 4.4. Минимальный контракт API

| Группа | Маршруты (проектные) | Семантика |
|---|---|---|
| System | `GET /api/v1/status`, `GET /api/v1/capabilities` | Состояние и доступные возможности |
| Settings | `GET/PATCH /api/v1/settings` | Тема, режим, параметры, revision |
| Characters | `GET/POST /api/v1/characters`, `GET/PATCH /api/v1/characters/{id}` | Библиотека/карточка |
| Import/export | `POST /api/v1/characters/import`, `POST /api/v1/characters/{id}/export` | Файл + отчёт совместимости |
| Stories | `GET/POST /api/v1/stories`, `GET /api/v1/stories/{id}` | Независимые прохождения |
| Chat | `GET /api/v1/stories/{id}/messages`, `POST /api/v1/stories/{id}/messages` | Постраничная история/добавление |
| Generation | `POST /api/v1/stories/{id}/generations`, `GET /api/v1/generations/{id}/stream`, `POST /api/v1/generations/{id}/cancel` | Создание, SSE, отмена |
| Branches | `GET/POST /api/v1/stories/{id}/branches`, `POST /api/v1/stories/{id}/branches/{branch}/activate` | Варианты истории |
| Prompts | `POST /api/v1/prompts/preview`, `GET /api/v1/generations/{id}/context` | Детерминированная сборка и инспектор |
| Memories | `GET/POST/PATCH /api/v1/stories/{id}/memories`, `POST /api/v1/stories/{id}/memories/search` | Источники, версии, поиск |
| Worlds | `GET/POST /api/v1/worlds`, `GET/POST /api/v1/scenarios`, `GET/PATCH /api/v1/stories/{id}/world-state` | Мир и текущая сцена |
| Director | `GET /api/v1/stories/{id}/director/log`, `POST /api/v1/stories/{id}/events/preview` | Диагностика и безопасный preview |
| Media | `GET/POST /api/v1/media`, `POST /api/v1/images/generate` | Импорт, галерея, генерация |
| Editor | `GET/PATCH /api/v1/manuscripts/{id}`, `POST /api/v1/manuscripts/{id}/export` | Редактор и экспорт |
| Automation | `GET/POST /api/v1/automations`, `GET /api/v1/jobs` | Правила, задачи, журнал |
| Plugins | `GET/POST /api/v1/plugins`, `PATCH /api/v1/plugins/{id}/grants` | Манифест и разрешения |
| Backups | `GET/POST /api/v1/backups`, `POST /api/v1/backups/{id}/verify`, `POST /api/v1/backups/{id}/restore` | Снимок/проверка/restore |
| Diagnostics | `GET /api/v1/diagnostics/metrics`, `POST /api/v1/diagnostics/export` | Метрики без принудительной публикации истории |

Все мутирующие запросы несут CSRF-защиту и предикат ревизии (`If-Match` либо поле `expected_revision`). POST операций с повторными попытками использует `Idempotency-Key`; при конфликте отдаётся 409 и текущая ревизия. Для удалённых сетевых запросов отдельная политика: без разрешения пользователя никакого внешнего доступа.

## 4.5. Поток генерации и ошибки

События SSE: `generation.started`, `generation.delta`, `generation.reasoning` (только при явной поддержке), `generation.metrics`, `generation.completed`, `generation.cancelled`, `generation.failed`. Каждое событие содержит `event_id`, `generation_id`, последовательный номер и JSON payload; повторная доставка не создаёт дублей. Ответ можно сохранить как `partial` при обрыве. Служебные reasoning-каналы не смешиваются с репликами персонажа.

Единая ошибка: `code`, `message_ru`, `request_id`, `recoverable`, `details` (без секретов). Перечень: `model_unavailable`, `context_overflow`, `storage_conflict`, `transaction_recovery_required`, `permission_denied`, `plugin_error`, `image_engine_offline`, `invalid_import`, `generation_interrupted`.

## 4.6. Схемы сущностей и связи

| Сущность | Идентификаторы/состояние | Важные связи |
|---|---|---|
| Character | `character_id`, card version, base personality | история → snapshot характеристики; медиа; пресеты |
| Persona | Свободное общение пользователя от своего имени | без обязательной отдельной карточки/переключаемых пользовательских персон |
| Story | `story_id`, активная ветвь и revision | мир, сценарий, сцены, сообщения, память |
| Message | `message_id`, `branch_id`, автор и revision | ответ, источник факта, альтернативные варианты |
| Event | `event_id`, game_time, affected entities | причины, последствия, журнальные записи |
| MemoryFact | утверждение, `knower_id`, confidence, source_ids | история, события, секреты, отменённые версии |
| Relationship | `party_ids`, narrative, metrics | история изменения, источники эпизодов |
| WorldState | текущее время, location, factions, flags | события, лорбук, RPG-стейт |
| MediaAsset | checksum, relative_path, type, metadata | карточка, событие, сцена |
| Job | idempotency, priority, state, retry_policy | память, режиссёр, backup, image |

**Инвариант знания:** запись факта в объективном состоянии мира не делает её автоматически известной каждому NPC. **Инвариант истории:** переключение ветви не должно удалять параллельную линию. **Инвариант пользователя:** модель не пишет действия или реплики пользователя без отдельной команды.

# 5. Правила разработки и контроля качества

## 5.1. Контракт прежде реализации

Каждая подсистема начинает работу с JSON Schema/OpenAPI и unit-тестов для доменных инвариантов. React использует сгенерированные TypeScript-типы API, а backend — валидируемые модели. Нельзя напрямую импортировать внутреннюю структуру storage в UI.

## 5.2. Quality gates каждого этапа

1. Приняты интерфейсы и миграции формата данных.
2. Выполнены обязательные unit/contract-тесты соответствующего модуля.
3. Существующие тесты предыдущих компонентов остаются зелёными.
4. Изменения данных обратимы либо имеют план восстановления.
5. Добавлены сценарии ошибок, а не только позитивный путь.
6. Документация обновлена; идентификаторы требований связаны с тестами.
7. Сборка этапа считается **внутренней**, не публичным релизом.

## 5.3. Рекомендуемые инструменты контроля

Python: `pytest`, `ruff`, `mypy`/`pyright`, `jsonschema`, проверки конфигурации. Frontend: `Vitest`, `Testing Library`, `Playwright`, `ESLint`, TypeScript strict. Общие схемы: JSON Schema и OpenAPI. Для производительности: собственный benchmark runner, замеры first-token latency и tokens/s, Windows Performance Counters/доступные телеметрические средства. Конкретные версии инструментов фиксируются после проверки совместимости в lock-файлах; не надо утверждать их по памяти.

## 7.1. Основная диаграмма зависимостей

```text
01 Bootstrap ──► 02 JSON ───► 03 LM Studio ─┐
                  │                         ├──► 06 Chat ───► 07 Prompts ───► 08 Memory
                  ├──► 04 UI ───► 05 Cards ┘                          │           │
                  │                                                   └────┐      ▼
                  └──────────────────────────────────────────────────────► 09 Worlds
                                                                          │

                                                                          │
                                                                          ▼
                                                                      11 RPG

03 + 04 + 05 + 09 ──► 12 Media ──► 13 Editor ──► 14 Plugins/Automation
                                            \___________________________/
                                                         │
                                                         ▼
                                                 15 Packaging/Backup
                                                         │
                                                         ▼
                                                  16 Full Acceptance
```

Условная схема отражает зависимости, но не запрещает заранее проектировать API последующих модулей. В частности, контракты memory/world следует формировать уже во время создания chat/story, иначе миграции JSON будут неоправданно дорогими.

## 7.2. Критические архитектурные решения до массовой реализации

| ID | Решение | Предварительная рекомендация | Граница допуска |
|---|---|---|---|
| ADR-01 | Транзакционность JSON | immutable сегменты + журнал + generation manifest | Воспроизводимый recovery после kill |
| ADR-02 | Схемы данных | versioned JSON Schema + typed backend/frontend | Нельзя тихо менять обязательные поля |
| ADR-03 | Реактивные события | типизированная event bus с event_id/idempotency | Нет дублирования после рестарта |
| ADR-04 | Контекст | stateless Chat Completions + серверный prompt builder | Каждый ответ имеет трассируемый prompt |
| ADR-05 | Память | provenance + scope + факт/убеждение | Отсутствует утечка секретов NPC |
| ADR-06 | Скрипты событий | декларативный AST, без eval | Предсказуемая детерминированная логика |
| ADR-07 | Плагины | declarative для недоверенных; доверенный код отдельно | Запрет обхода разрешений без ОС-изоляции |
| ADR-08 | Изображения | независимый локальный adapter | Не выгружать модели LM Studio |
| ADR-09 | Portable | frozen one-folder runtime в ZIP | Работает без dev-инструментов |
| ADR-10 | Обновления | manual replace + migration + recovery | Нет потери пользовательских данных |

Формальные связи «один REQ-ID → один или более тестов» формируются не позже начала реализации соответствующего этапа. Требования не удаляются и не переводятся в необязательные без отдельного решения владельца.

## 9.3. Fault-injection сценарии JSON и очередей

- Kill процесса до записи staging-файла, после записи staging, после commit-маркера и перед публикацией последнего файла.
- Недостаток места при сохранении сообщения, при backup, при индексации и при ручном обновлении.
- Переименование/удаление картинок и порча отдельного сегмента истории.
- Конфликт двух вкладок с ревизиями `n` и `n+1`; конфликт должен объясняться пользователю, а не «последняя запись побеждает».
- Рестарт во время асинхронной задачи memory/director/backup: idempotency предотвращает повторное применение эффектов.
- Ошибка локального генератора изображений: текстовая модель LM Studio и история остаются нетронутыми.

## 9.4. Производительность: не придумывать цифры

Эталонная система: Windows, i5-11400F, RTX 5070 12 ГБ, 32 ГБ RAM, Dolphin 2.9.3 Mistral Nemo 12B Q5_K_M. Базовые контексты **8192** и **16384** токена с резервом ответа **1024–2048**; дальнейшие значения определяются экспериментально.

План замеров: холодный/тёплый старт; TTFT; средняя и p95 задержка отправки запроса; tokens/s; RAM/VRAM; отмена; сводки и memory extraction; фоновые инструменты; реакция UI при 10k+ сообщениях; индексирование/восстановление; изображения при занятой VRAM. Три профиля: экономичный, сбалансированный, максимальное качество. Результаты заносятся в report с исходными условиями и версией модели.

**Предлагаемая цель качества:** отсутствие известных блокирующих/критических дефектов и полный проход AT-01–16. Пороговые задержки и процент покрытия unit-тестами устанавливаются на основе измеренного baseline и согласуются отдельно; неподтверждённые значения не объявлять гарантиями.

# 10. Версионирование, совместимость и миграции

1. Версии приложения `1.0.0` и схем данных `schema_version` независимы.
2. Чтение JSON старой версии сопровождается миграцией, предварительным backup и журналом действий.
3. Миграции должны быть повторяемыми и проверенными на копии реальных пользовательских данных; после неудачи должна оставаться восстановимая старая версия.
4. Импорт/экспорт карточек SillyTavern V1/V2/V3 и лорбуков выполняется адаптерами, не разрушая расширенных полей. Для неподдерживаемого переноса выдаётся точный отчёт.
5. Исходные stories и media не должны зависеть от расположения portable-папки или текущего имени персонажа.
6. Механизм ручных обновлений **не** обращается к интернету самостоятельно.
